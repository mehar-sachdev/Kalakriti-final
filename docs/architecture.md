# Architecture

```
Kalakriti storefront (frontend/index.html, real product data & images)
        |
        |  💬 Kalakriti AI floating widget  ->  POST /api/chat  (fetch, same origin)
        v
FastAPI (backend/main.py) — one process serves the site AND the API
        |
        +--> GET /products, POST /orders        (legacy e-commerce API, preserved,
        |                                         Supabase REST with local-catalog fallback)
        |
        +--> POST /api/chat  ->  RAGEngine.query()
                    |
                    +--> Structured product layer (backend/rag/products.py)
                    |      price filters, region/city/craft lookup, competitor-price
                    |      comparison — computed exactly from data/metadata/products.json,
                    |      never left to vector search to get a number right
                    |
                    +--> Department-aware retrieval (backend/rag/engine.py, retrieval.py)
                    |      embed question -> pgvector HNSW search (category-filtered)
                    |      -> similarity cut-off -> de-duplication
                    v
        Supabase Postgres + pgvector (schema "rag", isolated from the storefront's
        own "products"/"orders" tables - different credentials, different job)
                    |
                    v
        Ollama Cloud LLM (gpt-oss:20b) - grounded prompt, [n] citations,
        illustrative competitor prices always labelled as such
                    |
                    v
        {answer, products[] (cards + #product-<id> links), sources[]}
                    |
                    v
        Widget renders the answer, product cards (image, price, illustrative
        competitor price struck through), "View →" opens the SAME product modal
        the storefront already uses (openProduct()), no separate UI.
```

See [docs/architecture.svg](architecture.svg) for the ingestion-side diagram (documents -> Docling ->
validate -> chunk -> embed -> pgvector), which is unchanged in shape from the RAG framework this project
is built on; only the document categories changed (product/competitor/regional/craft/artisan instead of
department policy folders).

## Two backends, deliberately kept separate

| | Legacy storefront API | RAG assistant |
|---|---|---|
| Endpoints | `GET /products`, `POST /orders` | `POST /api/chat`, `GET /api/categories`, `/api/documents`, `/api/stats`, `/api/sources/{id}` |
| Data | Supabase `products`/`orders`/`artisans`/`inventory_transactions` tables (REST API), or the local `data/metadata/products.json` catalogue when Supabase isn't configured | Supabase Postgres **pgvector**, schema `rag`, reached only via a direct Postgres connection string |
| Credentials | `SUPABASE_URL` + `SUPABASE_KEY` (anon/REST) | `SUPABASE_DB_URL` (direct Postgres) |
| Why separate | This is the project's original e-commerce backend - preserved, not replaced. Mixing it with the vector store would couple two unrelated concerns and risk one credential leaking into the other's blast radius. | |

`backend/services/catalog_service.py` is the seam: it calls Supabase when configured, and self-heals a
real bug found in the original code (9 of 60 product image paths were wrong) by always resolving the
image from the authoritative local catalogue, regardless of what is stored in Supabase.

## The document corpus

```
documents/
  product/      146 DOCX (one per catalogue item) + products_catalog.xlsx
  competitor/   competitor_pricing.xlsx (every row labelled "Illustrative / Academic
                Demonstration Data") + methodology_note.docx (the disclaimer, in full)
  regional/     6 DOCX, one per region, listing its real cities and crafts
  craft/        9 DOCX, one per craft category (Textile, Pottery, Metalwork, ...)
  artisan/      artisans_directory.xlsx, unique artisans derived from the products
```

All 165 files are generated by `scripts/generate_documents.py` from one authoritative source,
`data/metadata/products.json` (built by `scripts/build_catalog.py` from the storefront's own
original product data) - there is exactly one version of every product's facts, reused by the
frontend, the RAG documents, and the structured comparison logic. Regenerating the corpus after
changing a product is `python scripts/build_catalog.py && python scripts/generate_documents.py`.

## Why product filtering/comparison is not "just RAG"

Vector search answers "what is this product like", not "which catalogue price is largest".
`backend/rag/products.py` detects price-filter and competitor-comparison questions with a small,
conservative regex-based intent classifier and computes the answer directly from the catalogue;
the LLM is then asked to phrase a sentence around facts it is handed, not to do arithmetic or
recall an exact number from a paragraph. See [docs/rag_pipeline.md](rag_pipeline.md) for the detail
and `tests/test_products.py` / `tests/integration/test_real_corpus_pipeline.py` for what is tested.

Live competitor-price questions use `backend/rag/web_prices.py` only when the shopper explicitly asks
for current or comparative pricing and names one catalogue product. Ollama Web Search/Web Fetch runs
server-side; a result is exposed only when an INR price is present in a fetched, relevant product page,
with its source URL and check time. Search failures preserve the RAG answer and do not invent a price.
New academic/demo products have no synthetic competitor reference price.

## Security model

* Secrets only from `.env` / environment; `SecretStr` keeps them out of `repr()`; a logging filter
  masks connection-string passwords, `Bearer` tokens and any registered secret in every log line
  and every API error.
* The RAG vector store is reached only through a server-side Postgres URL, in its own schema, with
  RLS on and `anon`/`authenticated` privileges revoked (`supabase/migrations/`). It never uses the
  Supabase REST/anon key.
* Everything the storefront itself needs (`/products`, `/orders`, `/api/chat`) is public with no key,
  because there is nothing confidential in a product catalogue and illustrative pricing data.
  `POST /api/ingest` (re-running ingestion from the running server) is the one gated, opt-in,
  admin-only action.
* The chat widget renders every piece of server text through `textContent`/DOM construction, never
  `innerHTML` - verified in a headless-browser test that a deliberately hostile answer produced no
  injected `<img>`/`<script>` elements.
